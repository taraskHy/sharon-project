### Blocker A (scoring validity, all 67 cases) — the target may be unreachable

This REOPENS a question the 2026-08-23 session recorded as closed. That session
concluded `selected=None` was harmless because "the histogram choice does not
affect the explanation score Erik recorded." The smoke run contradicts the
premise, and the contradiction is in the repo's own definitions:

- `schema.py:87` `explanation_weight` docstring: *"0 means all points sit on
  the selection and the explanation (if required) acts as a gate."*
- `gradingpack.py:225` emits `explanation weight 0` into every pack's
  `scoring_rules` — all 67 cases.
- `grade.py:457` composes the production score as
  `w = q.explanation_weight`; with `w = 0` no explanation points are awarded.
- `cases_inputs.jsonl`: `selected = None` for 67/67 cases.

So the pack the model reads declares that all 4 points sit on a selection the
model is never shown, while the explanation it *is* shown is declared weight 0.

The labels are not explanation scores either: `final_labels.json` carries
`ground_truth_source: "original_instructor_grade"` with `rubric_decisions: []`,
i.e. Erik's original whole-sub-item grade. `cases_labels.jsonl` still has
`score: null`, `rubric_met: null`, `label_status: NEEDS_OWNER_LABEL`, and no
`selection_correct` key — so `validate_grade` is called with
`selection_correct=None` as well.

Empirically: all 5 parsed grades across both working candidates were exactly
0.0. The one "exact match" (gemini on e003_q2_r6) is the instructor-0 case and
matches by construction. Sonnet's evidence string on e007 names the mechanism
directly: *"doesn't identify the correct image (F)"* — it looked for the
selection, did not find it, and withheld all credit. That is the pack's stated
rule applied correctly to an input missing the only scoring-relevant field.

Unresolved and NOT for me to settle: scores are {0, 2, 4} out of 4. A pure
selection-correct/incorrect rule yields only {0, 4}, so the 2/4 implies partial
credit from somewhere the machine-readable pack does not encode. Either
`explanation_weight = 0` is wrong for these questions, or `selected` must be
populated, or the instructor's scheme is not representable by the current pack.
Owner decision.

### Blocker B (transport) — openai/gpt-5.6-luna-pro cannot run

All 3 calls rejected HTTP 400 before inference, $0 billed:

    Invalid schema for response_format 'GradeResult':
    In context=(), 'additionalProperties' is required to be supplied and to be false.

The emitted `GradeResult` JSON schema omits `"additionalProperties": false`,
which OpenAI-family strict `json_schema` mode requires. Provider: Azure.
This is a harness schema-emission gap, not a model property.
Fixing it changes `schema_sha256` -> `config_hash` -> `run_id`, so it is an
owner decision, not a mid-run patch.

### Blocker C (route) — reasoning tokens starve the 600-token budget

`build_route` (`benchmark/runner.py:311`) passes `reasoning=spec.reasoning`,
and `bench run` exposes no `--reasoning` flag, so spec.reasoning is always None.
The production `models.toml [models.grade_primary]` setting
`reasoning = {effort = "none"}` is therefore NOT applied to benchmark runs.

Consequence: reasoning consumed 1106 of gemini's 1262 output tokens (88%) and
398 of sonnet's 507 on e002. sonnet's e003 call hit finish_reason=length at
max_tokens=600 and was lost. gemini returned `evidence: null` on all 3 cases
despite `evidence_policy: required` — consistent with content starvation.
