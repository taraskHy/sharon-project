# Structured Output + Serving Stacks for Self-Hosted Vision Models (verified July 12, 2026)

All sources fetched live on 2026-07-12. Key takeaway up front: **vLLM is the recommended university-server stack (TGI is officially dead for new work); llama.cpp-server or LM Studio (now free for work use) are the best Windows/CPU dev options; Ollama works but has silent-truncation and Intel-iGPU quirks worth engineering around.**

## 1. vLLM — best-in-class structured output for the GPU server target

- **Structured output API**: vLLM implements structured outputs via **xgrammar** or **guidance** backends with an `auto` mode that picks per request. Two request forms on the OpenAI-compatible endpoint: standard `response_format: {"type": "json_schema", ...}` (accepts Pydantic-derived or raw JSON Schema), or `structured_outputs` in `extra_body` with `choice | regex | json | grammar | structural_tag` options. Deprecated old fields (`guided_json` etc.) were **removed in v0.12.0** — new code must use `structured_outputs` / `response_format`. Source: https://docs.vllm.ai/en/latest/features/structured_outputs.html (fetched 2026-07-12).
- **xgrammar** is the default backend across vLLM/SGLang/TensorRT-LLM in 2026 and the fastest for most schemas (JIT-compiled pushdown automaton, effective grammar caching). Sources: https://developers.redhat.com/articles/2025/06/03/structured-outputs-vllm-guiding-ai-responses ; https://arxiv.org/pdf/2411.15100 (XGrammar paper).
- **Images on the OpenAI endpoint**: `"type": "image_url"` with HTTP URLs or base64 data URIs; local files via `file://` only with `--allowed-local-media-path`. **Multi-image per request is supported** — cap with `--limit-mm-per-prompt.image N` (e.g. 2+ per request for multipage exams; Qwen2-VL-family models support multiple images). Optional per-media `uuid` field enables caching across requests. Source: https://docs.vllm.ai/en/latest/features/multimodal_inputs.html (fetched 2026-07-12).
- **Structured output + VLMs**: guided decoding is applied at the sampling/logits stage on *output* tokens, so it is orthogonal to image inputs — nothing in the docs restricts it for multimodal models, and it's routinely used with Qwen-VL models. Known history: issue #13038 ("vllm doesn't honor the specified json schema using outlines/xgrammar with qwen 2.5 vl", vLLM 0.7.2, Feb 2025) reported *intermittent* schema violations (string instead of list); it was closed stale and pertains to the old V0 engine — https://github.com/vllm-project/vllm/issues/13038. On the current V1 engine the practical gotchas are **schema-feature support**, not vision: xgrammar historically rejected/ignored `minItems`, `maxItems`, `minLength`, `maxLength`, `pattern`, `uniqueItems` etc. (now largely added, with auto-fallback to the guidance backend for unsupported features, and a `has_xgrammar_unsupported_json_features()` utility) — see https://github.com/vllm-project/vllm/issues/16880 , https://github.com/vllm-project/vllm/issues/12201 , https://github.com/vllm-project/vllm/issues/26421 , https://github.com/vllm-project/vllm/issues/45592 (open 2026 issue: `pattern` on string items can cause `maxLength` to be ignored). **Recommendation: keep the grading schema simple — types, enums, required — and avoid length/pattern constraints.**

## 2. Ollama — convenient, with real pitfalls

- **Structured output**: `format` parameter accepts a full JSON Schema (constrained decoding), "more reliability and consistency than JSON mode." **Explicitly works with vision models** ("Vision models accept the same `format` parameter, enabling deterministic descriptions of images" — the launch blog demos llama3.2-vision image→schema extraction). Docs recommend: also put the schema in the prompt, use Pydantic/Zod, **temperature 0**. Sources: https://docs.ollama.com/capabilities/structured-outputs ; https://ollama.com/blog/structured-outputs (both fetched 2026-07-12).
- **OpenAI-compat endpoint** (`/v1/chat/completions`): vision works with **base64 images only — image URLs are NOT supported**; docs show a `qwen3-vl:8b` vision example. The feature list advertises "JSON mode"; however the blog explicitly demonstrates `client.beta.chat.completions.parse()` with Pydantic (which sends `json_schema`), so schema-constrained output does flow through the OpenAI layer. `tool_choice` and `logprobs` unsupported. Source: https://docs.ollama.com/openai (fetched 2026-07-12).
- **num_ctx pitfall (critical for multipage scans)**: "The OpenAI API does not have a way of setting the context size" — you must bake `num_ctx` into a Modelfile (`ollama create`) or set `OLLAMA_CONTEXT_LENGTH`. Default context is ~4096 (recent versions auto-scale with VRAM), and **overflow is silently truncated from the start — no error**. Vision tokens for several scanned pages can blow past 4k easily, so this is a top failure mode: the model would "grade" with pages silently dropped. Sources: https://docs.ollama.com/context-length ; https://www.autodidacts.io/increase-ollama-context-length-num-ctx/ ; https://docs.ollama.com/openai.
- **Quality caveats**: gpt-oss models frequently break schema compliance in Ollama (Harmony reasoning traces leak) — prefer Qwen-family; https://www.glukhov.org/llm-performance/ollama/ollama-gpt-oss-structured-output-issues/ ; https://github.com/ollama/ollama/issues/8063.
- **Windows + Intel iGPU**: experimental **Vulkan** landed in 0.12.6 (Oct 15, 2025), opt-in via `OLLAMA_VULKAN=1` from 0.12.11; per current official docs it's **enabled by default when the Vulkan backend is installed** ("Additional GPU support on Windows and Linux is provided via Vulkan"; disable via `OLLAMA_VULKAN=0`). Intel GPU support is soft — docs give Linux Intel driver instructions without firm support claims, and there's an open Windows hybrid-graphics bug where Vulkan wrongly selects the Intel iGPU over a dGPU with ~9-12x slowdown (https://github.com/ollama/ollama/issues/16667). Sources: https://www.phoronix.com/news/ollama-Experimental-Vulkan ; https://docs.ollama.com/gpu (fetched 2026-07-12).
- **CPU expectations for 7-8B VLMs**: Q4 7-8B decodes at roughly **5-12 tok/s** on desktop CPUs; the bigger cost for exams is **image prefill** (vision encoding + thousands of image tokens per scanned page) — expect tens of seconds to minutes per page CPU-only; downscaling scans (e.g. long side ~1000-1300px, or 640x640 for speed tests) materially helps. Sources: https://dev.to/mrzaizai2k/run-qwen2-vl-on-cpu-using-gguf-model-llamacpp-bli ; https://singhajit.com/llm-inference-speed-comparison/.

## 3. HF TGI — do not adopt; llama.cpp server — strong Windows/CPU option

- **TGI is in maintenance mode** (announced ~Dec 11, 2025; README banner verified today): "text-generation-inference is now in maintenance mode... minor bug fixes, documentation improvements and lightweight maintenance tasks" only; HF explicitly recommends **vLLM, SGLang, llama.cpp, MLX** instead. Last release 3.3.7 (Dec 19, 2025). Its Guidance feature (grammar-constrained JSON via `/generate` `grammar` param or tools) exists but is now frozen tech. Sources: https://github.com/huggingface/text-generation-inference (fetched 2026-07-12) ; https://huggingface.co/docs/text-generation-inference/conceptual/guidance.
- **llama.cpp (llama-server)**:
  - **Grammar/JSON schema**: `--grammar` (GBNF), `--json-schema`, per-request `grammar`/`json_schema` fields on `/completion`, and OpenAI-compatible `response_format` supporting `{"type":"json_object"}` and `{"type":"json_schema", "schema": {...}}` — note the slightly nonstandard shape (`schema` key directly, vs OpenAI's nested `json_schema.schema`; some clients need adjustment). Grammar is enforced at sampling, so it composes with vision inputs. Source: https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md (fetched 2026-07-12).
  - **Vision (mtmd)**: llama-server serves multimodal via OpenAI-compatible `/chat/completions` with `image_url` (base64 or local). Supported VLMs include **Qwen2-VL, Qwen2.5-VL (3B/7B/32B/72B), Qwen3-VL (dense + MoE, merged PR #16780)**, Gemma 3/4, InternVL 2.5/3, Pixtral, Mistral Small 3.1, SmolVLM, Moondream2. Load with `-m model.gguf --mmproj mmproj.gguf` or `-hf <repo>` (mmproj auto-downloads). Sources: https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md ; https://github.com/ggml-org/llama.cpp/pull/16780.
  - **Windows builds/Vulkan**: latest release **b9977 (July 12, 2026)** ships official Windows x64 binaries for **CPU, Vulkan, CUDA 12.4/13.3, SYCL, OpenVINO, HIP** — so Intel iGPU can be driven via the Vulkan build (or SYCL/OpenVINO for Intel-specific paths) with zero compilation. Caveat: community reports of Vulkan buffer-allocation failures with qwen2.5-vl on some Windows APU/iGPU setups — validate, and fall back to the CPU build (63GB RAM is ample for a 7-8B Q4 VLM + long context). Sources: https://github.com/ggml-org/llama.cpp/releases (fetched 2026-07-12) ; https://simonwillison.net/2025/May/10/llama-cpp-vision/.

## 4. LM Studio — friendliest Windows dev option, now license-clean

- **License**: free for personal **and work/commercial use since July 8, 2025** (commercial-license requirement removed) — university use is fine; paid Teams/Enterprise plans exist only for SSO/private sharing. LM Studio itself is proprietary freeware (the app isn't open source), but it runs open models via open engines (llama.cpp/MLX). Source: https://lmstudio.ai/blog/free-for-work (fetched 2026-07-12).
- **OpenAI-compat server** on localhost:1234 (`lms server start` or headless daemon); **structured output via `response_format.json_schema`** on `/v1/chat/completions`. Engine detail: **GGUF models use llama.cpp's grammar-based sampling; MLX models use Outlines**. Documented caveat: "Not all models are capable of structured output, particularly LLMs below 7B parameters." Vision GGUF models (Qwen-VL family etc.) are supported through the same llama.cpp mtmd stack, so schema + image requests work. Sources: https://lmstudio.ai/docs/developer/openai-compat/structured-output (fetched 2026-07-12) ; https://lmstudio.ai/docs/python/llm-prediction/structured-response.
- Community reporting suggests LM Studio's Vulkan runtime on Windows is currently *more* stable for Intel GPUs than Ollama's. Source: https://vucense.com/dev-corner/ollama-on-windows-2026-install-guide/.

## 5. Recommended JSON-reliability pattern for open VLMs

Research consensus (2024-2026): **constrained decoding guarantees syntax but can tax reasoning quality** — Tam et al., "Let Me Speak Freely?" (EMNLP 2024 Industry, https://aclanthology.org/2024.emnlp-industry.91.pdf) showed JSON-mode helps classification but hurts reasoning; follow-ups report 10-30% degradation on reasoning-heavy tasks under strict constraints and a "format tax" (https://arxiv.org/pdf/2604.03616 , https://arxiv.org/pdf/2604.06066); CRANE (https://arxiv.org/html/2502.09061v3) proposes letting the model reason freely before constraining. For a grading task that judges handwritten explanations semantically, the recommended pattern is:

1. **Use constrained decoding (json_schema) as the transport guarantee** — it's free insurance for parseability on all four stacks.
2. **Design the schema so reasoning precedes verdicts**: put a free-text `reasoning`/`transcription` field *before* the `score`/`answer` fields in the schema property order, so the model "thinks" inside the JSON before committing (mitigates the Tam et al. effect).
3. **Also state the schema in the prompt** (Ollama and TGI docs both explicitly recommend this — grounding improves field-level semantics that grammars can't enforce), and **set temperature ~0**.
4. **Keep schemas simple** (types/enums/required; avoid minItems/pattern/length constraints) to dodge xgrammar/backend feature gaps.
5. **Layer validate-and-retry on top** (Pydantic validation + one re-ask on failure) — constrained decoding guarantees syntactic validity, not semantic validity (wrong question IDs, hallucinated fields' *content*), so a cheap validation pass against the exam's known question list is still needed.
6. **Constrained decoding + vision tokens**: no architectural conflict (grammar masks output logits only), and Ollama/vLLM/llama.cpp all officially support schema+image requests; the observed failure modes are (a) old vLLM V0 intermittent non-enforcement (#13038, fixed era), (b) unsupported schema keywords silently relaxed, (c) repetition/whitespace loops under grammar pressure — TGI docs recommend `repetition_penalty`/`frequency_penalty` if that appears.

## 6. Mapping to your three deployment targets

- **(b) University Linux GPU server**: vLLM + a Qwen-family open VLM, `response_format json_schema` (xgrammar), `--limit-mm-per-prompt.image N` sized to max exam page count. Don't build on TGI.
- **(c) Windows laptop, Intel iGPU, 63GB RAM (dev)**: LM Studio (free for work, GUI, `response_format.json_schema`, Vulkan runtime) or plain llama-server Windows Vulkan/CPU binary for a scriptable, license-clean OSS-only path (MIT). Expect ~5-12 tok/s decode + slow per-page image prefill on CPU; downscale scans.
- **Ollama (either)**: workable, but you must bake `num_ctx` via Modelfile for the OpenAI endpoint, send images as base64 only, and beware silent context truncation on multipage exams and immature Intel-Vulkan device selection on Windows.

(Free hosted API options — target (a) — were outside this subtask's scope and researched separately.)
